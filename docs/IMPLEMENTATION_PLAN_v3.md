# 実装計画書 v3 — アイテム/装備の拡充と戦闘深化

作成 2026-06-14 ／ 正本仕様 docs/game-spec.md（依頼書v1.1）＋ docs/decisions.md（v2系の変更履歴）
本書は依頼者の「装備名を豊富にしつつ世界観を壊さず、バランスも壊さず、最終的に全部実装する」方針に対し、
3役割の設計会議（ゲームデザイン/バランス・世界観/ネーミング・システム設計）の意見を統合した実装計画です。

## 0. 設計会議の結論（合意事項）

| 論点 | 結論 | 理由（要約） |
|---|---|---|
| ダメージ式を指数式（atk÷2^(def/10)）に変えるか | **変えない**（減算式を維持＋改修） | エンドレス構造では高防御が指数的に効くと**B25が逆に易化**。敵全16種×深層曲線・harness(beatable/gear)・balance-sim を全面作り直しになる。投資対効果が最悪。 |
| 「1ダメージ問題」「装備差の滑らかさ」 | 乱数幅を**装備依存**に（`±max(1,round(atk*0.08))`）＋敵に**貫通/割合**特技 | 数式ではなく「DEFが上がりすぎた局面」の症状。敵側のレバーで解く方が筋が良い。 |
| 装備の単調さ | 各出現帯に**素装備＋効果違い装備**を重ねる | 「数字の大きい方を装備するだけ」を解消し、火力/耐性/特技の選択を生む。 |
| 新カテゴリの優先 | 野草・ふしぎ枝を先、伝え葉は限定、飾りは少数、地形/経済/なりきりは後段 | 戦術寄与とリスク（再生成連結性・UI・累積インフレ）の天秤。 |
| アイテム総量 | 把握可能な上限は**約60〜90種**（F0〜F7で台帳198件まで技術的に可能） | 識別なし前提では多すぎると逆に単調化。 |
| 実装の進め方 | **F0で無回帰リファクタ**→カテゴリを順に追加。各フェーズで全ハーネス＋sim＋実機を通過ゲートに | CORE/DOM分離・単一ファイル・既存受け入れ（独り言/ランキング/スマホ）を死守。 |
| FP主題 | FP本体は**非アイテムの最終ゴール**として温存。FPモチーフは最終装備セット🐾と気配演出に限定 | 「探している相棒」を安売りしない。 |

## 1. 確定する設計（仕様）

### 1.1 データモデル：`cat`（UI/動詞）と `effects[]`（宣言的効果）の分離

```
DATA.ITEMS[key] = {
  name, emoji, cat, minF, maxF, price,         // 既存＋price(価格帯:低/中/高/希少/伝説)
  verbs,                                        // 出す動詞 例 herb:['drink','throw']（未指定はcat既定）
  // 既存フラット（後方互換・温存）: satiety/hp/full/maxUp/dmg/stun/atk/def
  effects: [ { on, do, power, dur, range, radius, status, tag, chance, target } ],
  charges,                                      // ふしぎ枝の残り回数
  passive,                                      // 飾り/特殊装備の常時効果
  tags,                                         // 武器の対タグ特効・敵タグ照合
}
```
- **後方互換が最優先**：既存7アイテムのフラットフィールドは残す（harness data/items/gear が直接読む）。新カテゴリのみ `effects[]` を使い、`Core.act` の use 分岐は「effects があればディスパッチャ、無ければ従来処理」の二段。
- `cat` 追加：`herb`/`scroll`/`wand`/`charm`/`arrow`/`stone`（地形依存の `scent`/`box`/`morph` は後段）。

### 1.2 Core.act の拡張（action.type は1つだけ追加）

- 新規 `{type:'invoke', idx, verb}`（草drink/葉read/枝zap の統一入口）。`use`/`throw`/`place` は据え置き。
- 効果ディスパッチャ `Core._applyEffects(run, effects, ctx, events)`（CORE内・DOM非依存）。`do`: heal/satiety/status/damage/push/swap/warp/reveal/digWall/stat…。
- 対象/方向選択は `needDir` を `needSelect{mode:'dir'|'enemy'|'tile', candidates}` に一般化（CORE は候補を**純データ**で返し、入力UIはDOM側コールバック）。多くの枝は facing 固定で選択レス。

### 1.3 常時効果フック `Core._mods(run)`

- 装備3スロット（weapon/shield/**accessory**新設）＋一時バフ `player.buffs` を集計し `{atkAdd, atkMul, defAdd, satietyDrainMul, regenAdd, sightAdd, throwRange, evade, critChance, tagBonus, flags}` を返す純関数。
- `_playerAtk/_playerDef` をこれ経由に書き換え（**装備/バフ無しなら現行と同値**＝harness不変）。
- 名前付きフック差し込み点（既存メソッド末尾/直前に1行）：`damageCalc`/`onHit`/`onAttackCost`/`onAttacked`/`onTurnElapse`/`sight`/`throwResolve`。
- **特殊効果武器/盾**はキー名 if 分岐ではなく `effects[].on` で集約適用（武器が増えてもCOREコードは増えない）。

### 1.4 状態異常の一般化

- entity 共通 `statuses = {sleep,stun,confuse,slow,seal,poison,bind,...}`（残りターン）。
- **3クラス分類**で組合せ爆発を回避：①行動ゲート(sleep/stun=skip, confuse=方向ランダム, bind=移動不可) ②毎ターン効果(poison) ③AI修飾(seal=特殊AI無効, slow=隔ターン行動)。新状態は「どのクラスか」を宣言するだけ。
- 既存 `player.sleep`/`enemy.stun` は**ハイブリッド移行**（実体維持、新規4種のみ statuses。最終F7で統合）。harness items の `enemies[0].stun` 直読を壊さない。

### 1.5 ダメージ式の改修（指数化しない）

- `calcDamage(atk, def)` = `max(1, round((atk−def) ± max(1, round(atk*0.08))))`（乱数幅を装備依存に）。下限1は据え置き。
- **B25+を最適行動必須に**するレバー（ステータス以外を主軸）：深層大型獣に「DEF無視固定大ダメージ」「現在HP割合ダメージ」特技を一部付与／同部屋に大型2＋中型2の同時可視を許容（通路へ引く位置取り必須）／眠り等状態異常の再配置／はらぺこ罠密度を深層で上限寄りに／撤退コスト（階段遠配置）。

### 1.6 検証（harness/sim）拡張

- core-harness にカテゴリ別グループ追加（herb/scroll/wand/charm/gearfx/status）。既存グループ（data/mono/formulas/beatable/gear/items/gen/bot）は不変。
- **不変条件の死守**：地形変化（digWall/壁消し）後も**全床連結＝階段到達可能**をBFSで検証（生成時BFSを関数化して再利用）。独り言41行バイト一致・ランキング(deepest更新)は不変ゲート。
- balance-sim の smart bot 方策に「無力化アイテムを大型敵へ優先使用」「accessory装備更新」を追加し、難度カーブ（naive失速/smartのみ深層）維持を監視。

## 4. リスクと回避（死守事項）

1. **CORE純粋性**：reveal/dig/設置/視界 効果は run内データ（explored/tiles/field/selectMarks）だけ書く。document/window/canvasに触れない。core-harness の vm（document無し）で全グループ実行＝汚染は即検出。**各フェーズの絶対ゲート**。
2. **単一ファイル肥大**：データは生成ループ注入、COREはディスパッチャ＋フック集約で「カテゴリ増→コード増」を断つ。公開正本は単一HTML厳守（DATA別ファイル化はしない）。
3. **状態異常の組合せ爆発**：3クラス分類で分岐をクラス数に固定。
4. **既存テスト回帰**：フラットフィールド・`stun`実体・`MONOLOGUE_LINES`は温存。F0で「既存7を新機構に通して全グリーン」を先に達成。
5. **バランス崩壊**：balance-sim の naive/smart 到達率を全フェーズで監視。デメリット飾りも入れてプラス偏重を避ける（引きの妙）。
6. **スマホUI**：動詞増は野草2/枝・葉1で実ボタン増最小。needSelectは正面/最寄り自動に倒し新UIを増やさない。識別システムは当面不採用（全識別済み）。
7. **未確認仕様の暴走**：地形/経済/変身（F8以降）は依頼者確認を挟む。「仕様を勝手に変えない／不明点は要確認」を厳守。

## 5. 要確認事項（依頼者へ）

1. **ダメージ式**：会議の結論どおり**指数式は採用せず**、減算式＋乱数幅装備依存＋敵特技でB25を難化、で進めてよいか。
2. **スコープの上限**：まずF0〜F5（特殊装備・ころがし石/矢・野草・ふしぎ枝・飾り）で約60〜80種を目標、伝え葉(F6)・状態異常統合(F7)まで。**なりきりパン228・地形・経済・店・識別はF8以降で別途確認**、でよいか。
3. **FP本体**：アイテム化せず「最深のゴール（非アイテム）」として温存し、FPは最終装備セット🐾＋気配演出に留める方針でよいか。
4. **装備の段階拡張**：武器/盾を3段→16段＋効果違いへ拡張（§8.4の仕様追加＝decisions.md記録）でよいか。
5. **ころがし石と既存「松ぼっくり投擲」の棲み分け**：木=投擲/石=ころがし/矢=arrow の3系統で役割分担、でよいか。
